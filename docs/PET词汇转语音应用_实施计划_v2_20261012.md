## 2. 核心约束（决定架构，不可绕开）

1. **TTS 必须后端调用** —— 浏览器直连会被 CORS 拦，且拿不到 WebSocket 握手。→ 必须有服务端（本地服务端也算）。
2. **pymupdf + ffmpeg 必须后端** —— 抽 PDF、拼音频，浏览器做不了。
3. **音质锁定** —— 退回浏览器 `speechSynthesis` 会变成系统机械音，不可接受。
4. 🔻 **（原 ffmpeg 必需性）已松动** —— ffmpeg 单文件实测 **83.6 MB**，但它只干「生成静音 + 拼接同参数 MP3」两件事，两者都可用纯 Python 替代（见 §9.5），**可砍掉 >50% 分发体积**。
5. 🔻 **出口 IP 连坐（已降级）** —— TTS 从**服务端出口 IP** 出网，该风险只在"匿名公开"时成立。本方案已明确不做公开上线，风险面缩到「自己 + 少量分享」，降为低风险。**但仍保留 `TTS_PROVIDER` 开关**：edge-tts 无 SLA、随时可能波动。
6. 🆕 **单条播放依赖时间轴** —— 「单条重听 / 单条循环」要求前端能 seek 到任意一条的起止位置，后端**必须**输出每条的时间戳。
7. 🆕 **iOS 自动播放限制** —— `onended` 里调用 `play()` 不在用户手势栈内，iPad 上会被拦。必须首次点击解锁，且全程**只用一个 audio 元素**。
8. 🆕 **规模是小时级** —— 全书 110 页 ≈ 2,100 词条 ≈ **4,200 次 TTS**，串行约 **2 小时**。不能是请求-响应。
9. 🔻 **形态未定** —— 「本地 Web / EXE / 纯 HTML 播放器」三选一或组合，见 §9.5。这一项会显著改变交付方式与分发体积（**20 KB ~ 180 MB**）。

### 3.1 分层与"复用"的真实边界

| 层 | 复用程度 | 说明 |
|----|----------|------|
| 合成链路（tts / make_silence / concat_files） | **算法复用，签名重构** | 逻辑不变，但 `tmp`/`OUT_DIR`/`PDF` 从全局改为**显式参数** |

### 3.2 自适应抽取层（M1 核心工作）

```python
def extract_pairs(path: str, idx: int, profile: PageProfile | None = None) -> ExtractResult:
    """
    策略链（依次尝试，任一成功即返回）：
      1) table_strategy : page.find_tables()  → 真正的表格单元格，抗版式变化（首选）
      2) column_strategy: 对词条 x0 做一维聚类，自动识别「左列 / 右列」主簇 → 替换写死的 x<250 / x>380
      3) profile        : 命中已知版式指纹（页面尺寸 + 列簇中心），直接用缓存好的参数
    失败时必须显式回报，绝不静默返回空表。
    """
    return ExtractResult(pairs=[...], strategy="table", confidence=0.93, warnings=[])
```

**硬性要求**
- **禁止裸坐标常量**。`left_x / right_x / y_gap` 一律由聚类产出，或来自 `profile`。
- **禁止静默失败**。`pairs` 为空 / 中英数量失衡 / 左列非拉丁居多 → 返回低 `confidence` + `warnings`，前端提示「本页需手动校对」并引导到编辑界面。
- **解析在子进程 + 硬超时 + 内存上限**内执行（防解析炸弹）。
- `norm()` 的连字替换（`ﬁ ﬂ ﬀ`）、表头过滤（`英文/中文`）保留，但表头词表改为可配置集合。

### 3.3 词级缓存（P0，同时解决性能与重复合成）

```python
word_key = sha256(f"{text}|{voice}|{rate}").hexdigest()[:16]          # 单个词条音频
page_key = sha256(canonical_json({"words":[word_key...], "gaps":[0.5,0.5]}))  # 整页成品
```
`data/cache/words/{k[:2]}/{k}.mp3`、`data/cache/pages/{k[:2]}/{k}.mp3`
**词级缓存比页级缓存命中率高一个数量级**：不同页/不同书共享同一个单词的音频；命中即零成本、零等待。v1 放在 P2，v2 提到 P0。

### 3.4 TTS Provider 抽象（双实现，同参数回退）

```python
class TTSProvider(Protocol):
    name: str
    async def synth(self, text: str, lang: Literal["en", "cn"], rate: float, out_mp3: str) -> None: ...

class EdgeProvider:   # edge_tts.Communicate(text, voice, rate=f"{rate:+.0%}")   ← 默认
class AzureProvider:  # SpeechConfig + speech_synthesis_voice_name
                      # + Audio24Khz48KBitRateMonoMp3（与 edge 输出格式对齐，保证可拼接）
```
- `TTS_PROVIDER=edge|azure` 环境变量切换；两者音色名相同。
- 重试策略沿用现有（4 次 + 指数退避 + 40s 超时）。
- **输出编码必须锁定为单一格式**（24 kHz / 48 kbps / mono MP3）。这是 §9.5「去掉 ffmpeg」的前提，也是将来换 Azure 时唯一要守的约束。

## 4. 接口契约（M1 必须冻结）

```
# 预置词库（只读）
GET  /lib/pages                       → [{page, topic, words, mp3_url, duration, tracks:[...]}]
GET  /lib/audio/{page}.mp3

# 上传与抽取
POST /upload?name=x.pdf  body=原始 PDF 字节  → 202 {doc_id, pages}
                                         Content-Type: application/pdf

GET  /preview?doc_id=…&pages=all      → { pages:[{page, topic, confidence, warnings,
                                                  pairs:[{i,en,cn}]}] }

# 合成任务（异步，非请求-响应）
POST /jobs                            → 202 {job_id, eta_seconds}
     { doc_id|lib, pages:[…], pairs_override?:{page:[…]}, provider, voice, rate }
GET  /jobs/{job_id}/events            → text/event-stream  进度流（SSE）
GET  /jobs/{job_id}                   → {status, progress:{done,total,current}, error}
GET  /jobs/{job_id}/result            → { pages:[ … ] }  ← 见下方结构
DELETE /jobs/{job_id}                 → 取消任务

# 下载
GET  /download/{job_id}/page003.mp3
GET  /download/{job_id}/all.zip                     # 含 manifest.csv
```
> 🔻 HMAC 签名 URL：**本地使用时不需要**（无枚举风险）。仅当将来真要远程分享再补，接口位置已预留。

**🔴 时间轴契约（v1 完全缺失，这是 M1 的冻结项）**

```json
{
  "job_id": "8f3c…",
  "pages": [{
    "page": 3,
    "topic": "Sports",
    "mp3_url": "/download/8f3c…/page003.mp3",
    "duration": 58.20,
    "tracks": [
      {"i": 1, "en": "peaceful", "cn": "宁静的", "start": 0.00, "end": 2.35},
      {"i": 2, "en": "...",      "cn": "...",    "start": 2.85, "end": 5.10}
    ]
  }]
}
```

计算规则（后端唯一权威，前端**不要自己猜**）：
- `tracks[i].start = 上一条的 end + GAP_WORD(0.5s)`；`end = start + 该词条时长`（该词条 = 英 + `GAP_EC(0.5)` + 中）。
- 时长优先用 **`mutagen.mp3.MP3(path).info.length`**（纯 Python，毫秒级，约 200 KB）；`ffprobe` 仅作兜底。
  *全书 2,100 个词条若逐次 spawn ffprobe，会白多花 1–2 分钟；mutagen 可忽略不计。*

## 7. 循环朗读状态机（v2 重写）

> v1 的 `breakIt` 布尔量有竞态：用户点停止的瞬间若音频正好自然播完，`onended` 先跑、`breakIt=true` 后落 → **标志残留** → 下次点播放"播一下就停"。
> v2 改用**代次计数器**，原理上不可能残留。

```js
let gen = 0;                        // 代次：任何 play/stop/切页都 +1
let mode = 'loopPage';              // single | loopPage | seqAll

function playAt(i) {
  const my = ++gen;                 // 本次播放的身份
  const t = currentTracks[i];
  audio.currentTime = t.start;      // 单条播放用 seek，不换 src（避免重下/重解码的空洞）
  audio.play();
  highlight(i);
  audio.onended = () => {
    if (my !== gen) return;         // 已被更新的播放或停止取代 → 静默退出
    if (mode === 'single')        playAt(i);
    else if (mode === 'loopPage') playAt((i + 1) % currentTracks.length);
    else if (mode === 'seqAll')   nextPageOrFinish(i + 1);
  };
}

function stop() { gen++; audio.pause(); }   // 无需清零任何标志
```

**iOS 解锁（必须做）**
```js
// 首次用户点击「开始」的手势栈内：
audio.src = firstClipUrl;
audio.play().then(() => audio.pause());
// 并且全程只用一个 audio 元素；多元素会被 iOS 逐个限制
```

**seqAll 必须按页懒加载**（v1 未定义数据来源）
110 页 × 约 400KB（实测均 389KB）≈ **42MB**，单个整包对手机不可接受。
→ 前端维护 `pageList / pageIndex`，播完当前页后 fetch 下一页（可在播当前页时预取下一 `src`），跨页无缝续播。

模式语义：`single` 只循环当前一条（听发音细节）／`loopPage` 本页循环（默认，最常用）／`seqAll` 全书顺序，到底结束。

## 8. 数据流

```
【预置词库】GET /lib/pages → 后端已有 110 页 MP3 → 返回带 tracks 的元数据
【自助上传】
  上传 PDF
    → 子进程抽取（自适应策略链，带超时）+ 页面识别
    → GET /preview 返回 {page, confidence, warnings, pairs}
    → 用户选页 / 编辑错词（pairs_override）
    → POST /jobs → 入队（并发 2–4）→ 202 + job_id
    → 后端逐词：查词级缓存 → 未命中才 TTS → 拼词条 → 拼整页
    → 产出 tracks 时间轴（mutagen 读时长累加）
    → SSE 推进度；GET /jobs/{id}/result 取结果
    → 前端循环朗读 / 下载
```

## 9. 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 前端 | **单文件 HTML + 原生 JS**（零框架） | 沿用既有偏好；**同源提供，彻底绕开 CORS** |
| 后端 | **纯标准库 `http.server.ThreadingHTTPServer`**（首选）／ Starlette · FastAPI（见 §9.1） | 零依赖、双击即用；**但只复用 jev 的启动器与连接层，请求层需重写** |
| 任务/队列 | 进程内 `asyncio.Queue` + 并发信号量 + 内存任务表 | 单进程即可；**不要开多 worker**（内存态会分裂），需要时才上 Redis |
| PDF 抽取 | PyMuPDF（`find_tables()` 优先 + 坐标聚类兜底） | 已验证，且 `find_tables` 天然抗版式变化 |
| TTS | **edge-tts（默认）**，Azure（可选开关） | §10 |
| 时长读取 | `mutagen`（约 200 KB，纯 Python） | 避免 2,100 次 `ffprobe` 子进程 |
| 音频拼装 | **优先纯 Python 字节拼接**；ffmpeg 作兜底 | §9.5，可省 83.6 MB |
| 缓存 | 文件系统（sha256 分目录） | 无需 DB |
| DB | **无**（localStorage 存偏好即可） | — |
| 启动器 | **复用 `start_jev.bat` / `stop_jev.bat` 改造为 `start_pet.bat`** | 已解决端口文件、PID、日志落盘、`pythonw` 无控制台、自动 kill 旧实例、自动开浏览器、失败转前台看错误 |
| 打包 | 单页 mp3 / 全书 zip（含 manifest.csv，列沿用 `page_idx,file,words,bytes,status`） | — |

### 9.1 服务端复用边界（🔻 已核实，修正 v2 的过度乐观）

v2 原话「`jev_stock_app.py` 已验证含后台线程与端口发布」**说法不准**，已按实测核实更正。

**jev 项目实测规模**：`jev_stock_app.py` **约 1,370 行 / 67 KB**，其中 **约 1,100 行（80%）是股票业务逻辑，与本项目完全无关**；真正的 HTTP 部分只有 **1106–1400 行，约 295 行**。

| jev 的组成 | 复用 | 说明 |
|------------|------|------|
| `start_jev.bat` / `stop_jev.bat` | ✅ **几乎全可复用** | 只改 3 个常量（脚本名 / 起始端口 / 标题）。与业务模型无关 |
| `_log` / `_out` / `_is_tty` | ✅ | `pythonw` 无控制台时 `sys.stdout is None` 的处理已踩过 |
| `Handler.log_message` 覆写 | ✅ | 默认写 `sys.stderr`，无控制台会抛 `AttributeError` 导致**每个请求都崩** |
| `_port_available()` / `bind_server()` | ✅ **尤其值钱** | Windows 上 `SO_REUSEADDR` 会让"已被占端口"也 bind 成功 → 旧实例抢答（"改了代码却不生效"），它用独占探测绕过了 |
| `main()` 的 `app.port` / `app.pid` / 自动开浏览器 | ✅ | |
| 「单文件 Python + 顶部内嵌 HTML」组织模式 | ✅ | |
| **`Handler` 请求层**（路由 / `_send` / `do_GET` / `do_POST`） | ❌ **重写** | 见下 |
| 股票业务逻辑 | ❌ | 约 1,100 行，无关 |

**「模型不一样」是根本性的**：

| 维度 | jev | 本项目 |
|------|-----|--------|
| 请求模型 | 无状态 / 同步 / 纯 JSON 短请求 | 文件上传 + **小时级后台任务** + 流式进度 |
| 传输 | JSON 进出 | 原始字节进 / 二进制 MP3 出 |
| 并发 | 一线程一请求（唯一线程只用来开浏览器） | 任务队列 + 并发信号量 |
| 响应 | `_send()` 固定带 `Content-Length`，**与 SSE 天然不兼容** | 需 `text/event-stream` + `flush` |
| 静态文件 | ❌ 无（`do_GET` 只服务一个内嵌 HTML，其余 404） | 需音频静态服务（可选 `Range`） |

→ **可复用的是「启动器 + 连接层」（约 230 行，纯赚）；「请求层」按重写估（约 200–300 行）。**

**🔴 同时实测发现一个坑（决定后端选型）**
pet 环境是 **Python 3.13.14**，而 **`cgi` 模块已在 3.13 被移除**（PEP 594）；`python-multipart` 也未安装。实测：

```
ModuleNotFoundError: No module named 'cgi'
ModuleNotFoundError: No module named 'multipart'
email.parser OK
```

→ 标准库**不再自带 multipart 解析**。但有一条干净的绕法：

| 方案 | 做法 | 结论 |
|------|------|------|
| **A. 原始字节当请求体**（推荐） | 前端 `fetch(url, {method:'POST', body: file})`，**不用 `FormData`**；服务端只 `read(Content-Length)` 流式落盘 | ✅ **完全不需要 multipart 解析**，纯标准库够用。前提：客户端是我们自己写的（成立） |
| B. 手写 multipart 解析 | 用 `email.parser` 或自写边界扫描 | ⚠️ 约 80–150 行且边界易错，只为省不到 20 MB 依赖，不划算 |
| C. 引入 Starlette / FastAPI | 原生 `UploadFile` / `StreamingResponse` / `StaticFiles` | 🟡 最省心；代价 `starlette+uvicorn+python-multipart` 约 3–5 MB（FastAPI 因 pydantic 约 20–25 MB） |

**选型结论**：走 **A**（纯标准库），仅在将来需要"从任意浏览器表单上传 / 要 API 文档"时才换 C。
配套要注意：SSE **不能**用 jev 的 `_send()`（固定 Content-Length），必须另写"写头 → 循环 `wfile.write` + `flush`"的流式路径。

### 9.5 应用形态（✅ 已定：**先做形态 ③**，详见《形态选型_Web_vs_EXE》与 §0.3、§19）

| 形态 | 给谁用 | 分发体积 | 关键约束 |
|------|--------|----------|----------|
| **① 本地 Web**（零依赖 `http.server`） | 你自己 | 需本机 Python + **153 MB** 依赖（实测） | 调试体验最好（浏览器 DevTools） |
| **② EXE**（PyInstaller `--onedir`，内部仍是本地 Web） | Windows 家长 | **约 90–180 MB**（估算） | 打包 +2~4 天；会遇到 SmartScreen / 杀软拦截 |
| **③ 纯 HTML 播放器**（+ 预生成 MP3） | **iPad / 手机家长** | **20–40 KB**（+音频 42 MB 可选按页给） | **完全离线可用**；iOS `file://` 行为**需实测** |

**关键洞察**：家长要的只是「循环听写」，而 MP3 已经存在（110 页 / 41.8 MB）。
→ **「抽取/合成」与「循环播放」可以拆开**：给家长的那一份可**完全不含 Python / pymupdf / ffmpeg**；EXE 也**不等于离线**（edge-tts 仍需联网），而 ③ 是真正离线的。

**体积机会（实测数据支撑）**

| 组件 | 实测体积 | 能否去掉 |
|------|----------|----------|
| `imageio_ffmpeg`（含 `ffmpeg.exe`） | **83.7 MB**（二进制单文件 **83.6 MB**） | ✅ 能——只需「生成 0.5s 静音」+「拼接同参数 MP3」：前者用一个**预置 5 KB 静音文件**，后者**MP3 是帧结构，纯 Python 字节拼接即可**（剥 ID3v2 与首帧 Xing/Info 再顺序拼接）。约 30 行代码 + 一组对比测试 |
| `pymupdf` | **52.9 MB** | ✅ 能（仅当用户不需要自己传 PDF 时）——抽取留在你这边跑一次 |
| `edge-tts` + `aiohttp` + `certifi` | 约 3 MB | ❌ 保留 |
| Python 3.13 基础环境 | 48 MB | ❌ ① 需要；②③ 不需要 |

**顺序建议**：**① 先跑通全链路 → ③ 发给家长（成本最低、覆盖 iPad）→ ② 视需要再打包。**

### 9.6 播放器前端（②③ 共享同一份代码）

循环朗读那套 JS（代次计数器 / iOS 解锁 / 懒加载）在 EXE 与纯 HTML 播放器里是**同一份**，写一次即可 → 形态切换几乎不增加前端工作量。

## 17. 输入格式扩展路线（txt / docx / jpg）

> 结论：都可行，且都比 PDF 简单。PDF 是最难的输入（坐标猜测 + 表格语义重建）。

| 格式 | 解析方式 | 格式约定 | 难度 | 质量风险 | 依赖 |
|------|----------|----------|------|----------|------|
| TXT | 按行读 + 按 `\t` 切 | 一行一条「英文[TAB]中文」 | 极低 | 无 | 标准库 |
| DOCX | 读两列表格（左英右中） | 两列表格 | 低 | 低（合并/多行单元格需容错） | `python-docx` |
| JPG（清晰扫描） | OCR → 坐标+文字 → 复用表格重建 | 平整清晰 | 中 | 低 | PaddleOCR / 云 OCR |
| JPG（随手拍） | 同上 | 倾斜/模糊/遮挡 | 中 | **高**（中文错字、列错位） | 同上 |

**关键说明**
1. **JPG 与扫描件是同一支线（v2 新增）**：现在扫描版 PDF 会静默返回 0 词条（无文字层）。用 `page.get_pixmap()` 渲染成图 → 走同一条 OCR → 坐标重建，**多写 5 行就把两者合并**，值得顺手做。
2. **OCR 输出的就是坐标化文字，与 `get_text("words")` 同源**，可直接复用自适应抽取层。
3. **OCR 方案二选一**：本地 PaddleOCR（免费、需装几百 MB 模型，适合自用）／ 云 OCR（按次付费、质量更高）。
4. **P1 编辑界面是 JPG 支线的准入前提**，不是可选优化。
5. **「无结构文本」是另一个功能，别混进来**：整段英文文章要做的是**整段朗读**（类似 TextSpeak），没有配对、没有单条循环。建议做成独立模式，别往配对解析器里硬套。
6. **建议顺序**：txt（半天）→ docx（1 天）→ jpg/扫描件（视 OCR 方案 1–3 天）。

## 21. 「上传自己的文件 → 生成新词库」设计（2026-10-12 追加）

> 配套图示：`D:\WorkBuddy\2026-10-12-08-47-56\pet-generator-design\index.html`
> 局域网可看：`http://192.168.3.98:8899/pet-generator-design/index.html`

### 21.1 结论：这个功能**不属于形态 ③**，需要新增「转换器」

形态 ③ 是纯静态 HTML：**没有后端、浏览器也不能往硬盘写文件**，所以"上传即生成"在它里面做不到。
需要新增一个跑在**电脑端**的「转换器」。三条硬约束（任一条都足以否掉纯前端方案）：

1. TTS 从浏览器直连会被 CORS 拦、也拿不到 WebSocket 握手；
2. PDF 解析与音频拼接浏览器做不了；
3. "生成词库"要落盘写文件 —— 浏览器没有这个能力。

**但要澄清一个容易混淆的点**：产出的**不是**"往云端插一条数据"，而是**一个播放器文件夹**：

```
packs/我的词库/
├── index.html          ← 复用现有播放器模板（换数据）
├── audio/p001.mp3 …    ← 新生成的音频
└── manifest.csv        ← 可选
```

### 21.2 五层流水线

| 层 | 做什么 | 状态 |
|----|--------|------|
| ① 抽取 | 按扩展名路由，归一成 `[{en,cn},…]`。PDF 用 `find_tables()` 优先 + x0 一维聚类兜底；DOCX 读两列表；TXT 按行按 Tab；JPG/扫描件走 OCR → 坐标 → 复用表格重建 | 🔻 **待做**（2–3 天）。现有代码把列坐标写死（`x<250 / x>380`），换版式必崩 |
| ② 校对 | 抽出"英/中"两列给人改错字、拆合并错的条目 → `words.json` | 🔻 待做（约 1 天）。**任意文件可用的前提，不可省** |
| ③ 合成 | 逐词 TTS；先查**词级缓存** `sha256(文本+音色+语速)` | 🟡 逻辑已有，待参数化 + 加缓存 |
| ④ 拼接 + 时间轴 | 拼整页 MP3 + 产出每条 `start/end`。两条路都验证过：合成时记录（mutagen）或事后反推（silencedetect） | 🟡 ④ 已验证（110 页 / 2078 条 / 0 异常 / 9 秒） |

**建议顺序**：先做 (b) 跑通并统计错词率 → 再决定是否投入 (a)。两者共用同一个核心脚本，先做 (b) 不浪费。

### 21.5 上传环节的技术约束（与 §9.1 一致）

Python 3.13 已移除 `cgi`（实测 `ModuleNotFoundError: No module named 'cgi'`），标准库不再自带 multipart 解析。
**绕法**：前端 `fetch(url, {method:'POST', body: file})` 把**原始字节**当请求体，服务端按 `Content-Length` 流式落盘 —— **完全不需要 multipart 解析**（前提：前端是我们自己写的）。
只有当"从任意第三方表单直接上传"成为需求时，才需要 `python-multipart` 或 Starlette/FastAPI。

### 21.6 诚实提醒

"上传任意 PDF 就能用"的**天花板不在程序，而在版式**。现有抽取规则对**这一份** PDF 可完全复现 manifest（110 页 0 处不一致），但换成页宽/边距不同的表就会同时踩空（实测列位置：左列 x∈[80,148]、右列 x∈[443,527]，硬编码阈值恰好落在两列之间的空白带里 —— 这是侥幸，不是稳健）。
→ **校对界面不是可选美化，而是该功能能否成立的前提。**

### 23.8 🔴 修复：「第一次点开始没反应」（2026-10-14）

**用户报告**："第一次按开始一直没反应，按暂停、再按开始才会播放" → **经核实完全成立**，是确定的 bug。

**根因**（`pet-player-sketch/index.html` 的 `playFrom()`，原代码）：

```js
function playFrom(k){
  if (!unlocked){                       // ← 罪魁：所谓「iOS 音频解锁」
    unlocked = true;
    audio.play().then(() => audio.pause()).catch(() => {});
  }                                     //    .then 是**异步**的（微任务）
  const t = tracks[k].start;
  if (hasAudio) { audio.currentTime = t + 0.02; audio.play().catch(() => {}); }
  ...
}
```

**首次点击的时序**：

| 步 | 发生的事 | 结果 |
|----|----------|------|
| 1 | 第 440 行 `audio.play()`，注册 `.then(() => audio.pause())` | Promise 挂起 |
| 2 | 第 443 行**同步**发出真实的 `play()` | 开始播放 ✅ |
| 3 | 微任务队列执行，第 440 行的 `pause()` 落地 | **刚播就被掐停** ❌ |

外加 `setPlaying(true)` 在**同步**路径里执行，所以按钮已经显示「⏸ 暂停」而实际无声 ——
"按暂停、再按开始"之所以有效，是因为此时 `unlocked` 已是 `true`，**跳过了解锁块**。

**修复**：**整块删掉**。理由 —— iOS 的解锁条件本就是「该元素曾在**用户手势里**成功 `play()`」，
而第 443 行的真实 `play()` 就在点击回调的同步调用栈里，**它自己就完成解锁**。
那个额外的 play/pause 不只是多余，还制造了竞态。

```js
function playFrom(k){
  const t = tracks[k].start;
  if (hasAudio){
    // 元数据未就绪时设 currentTime 会被忽略 → 就绪后补一次 seek
    if (audio.readyState >= 1){ try { audio.currentTime = t + 0.02; } catch(e){} }
    else audio.addEventListener('loadedmetadata', function(){
      if (playing){ try { audio.currentTime = t + 0.02; } catch(e){} }
    }, { once: true });
    audio.play().catch(err => {
      if (err && err.name === 'NotAllowedError') toast('浏览器拦了自动播放：请再点一次「开始」');
    });
  } else simT = t;
  showTrack(k); setPlaying(true);
}
```

此时 `audio.currentTime = t` **会被浏览器忽略** → 直接点第 30 条却从第 1 条开始播。
现在改为「元数据就绪后再补一次 seek」。

**为什么之前的自检没抓到（教训）**：旧探针只断言了
`按钮文字变成「暂停」`—— 而这个 bug 的表象恰恰是**「按钮说暂停、音频是静音」**，
断言选在了错误的观测点，所以 **11 PASS / 0 FAIL 却漏掉了它**。

### 23.9 修复「点词条重听却回到第一条」+ 底部迷你控制条（2026-10-14）

#### A. bug：点任意一条重听 → 实际回到第一条

**根因（两处叠加）**

1. **`ios Safari 会丢弃「元数据加载完成前」的 `currentTime` 赋值。** Chrome 会把它挂起、加载完再生效；Safari 直接丢。
2. **旧代码只在 `loadedmetadata` 事件里补 seek，而这个事件可能已经错过**——
   `openPage()` 里 `audio.src = ...` 之后才 `playFrom()` 注册监听，
   若 `loadedmetadata` 在这两步之间已经触发，**监听永远不会触发 → seek 永久丢失**。

一旦 seek 丢失，`tick()` 每帧读 `audio.currentTime` 仍是 0 →
`trackAt(0)` 推出第 1 条 → **`showTrack(0)` 把高亮和播放位置一起拽回第 1 条**，
表现为"点想重听的那一条，结果从第一条开始放"。

**修复：把 seek 从"依赖引擎语义"改成"自己记账 + 持续重试"**

```js
let pendingSeek = null;                        // 目标位置，未落地就一直保留

function applyPendingSeek(){
  if (pendingSeek === null || !hasAudio) return;
  if (audio.readyState < 1) return;            // 没元数据 → 交给 tick / 事件重试
  try { audio.currentTime = pendingSeek; } catch (e) {}
  if (audio.seeking || Math.abs(audio.currentTime - pendingSeek) < 0.3)
    pendingSeek = null;                        // 已落地
}
```

- `seekTo()`：设 `pendingSeek` → 立即尝试 → 没落地就挂 `loadedmetadata`/`canplay` 补一次
- `tick()`：**只要 `pendingSeek` 未落地，UI 一律按 `pendingSeek` 显示**（进度、时钟、高亮），
  每帧重试，绝不因为 `currentTime===0` 而回退高亮

**顺带修掉语义不符**：提示写的是「点任意一条重听」，但旧代码只在 `playing` 时才播，
暂停/停止状态下点词条**只 seek 不出声**（用户会以为"点了没反应"）。
现在行点击一律走 `playFrom(k)` → 点了就出声。

在 `_cdp_probe.py` 里劫持 `HTMLMediaElement.prototype.currentTime`：

### 23.12 ✅ 第三次定位成功：真凶是「服务器不支持 HTTP Range」（2026-10-14）

**用户实测的关键对照**：版本号是 `v2026-10-14.5`（确认是最新版），而
**双击 `packs\初中英语词汇表_第1页\index.html` 一切正常**；只有通过 HTTP 预览时才异常。

**真凶**：`python -m http.server`（`SimpleHTTPRequestHandler`）**不支持 HTTP Range，也不发
`Accept-Ranges: bytes`**。Chromium 因此把整个音频判为**不可 seek**：

```
audio.seekable.length === 1   但   audio.seekable.end(0) === 0     ← 可 seek 范围为空
```

于是 `audio.currentTime = t` 被静默忽略 → 「点某条重听 / 上一词下一词 / 暂停后恢复」
全部失效，并且**永远从 0 播起**。`file://` 打开不受影响（本地文件可随机访问），
所以这个问题**只在通过 HTTP 预览时暴露** —— 极易误判成"播放器逻辑有 bug"。

**证据（同一份包，只换服务器）**：

| 环境 | `seekable` | 暂停(idx=6, ct=22.06) → 再播放 |
|------|-----------|-------------------------------|
| `http.server`（无 Range） | `1(到 0.0)` | ❌ `ct=0.00`，`pending=19.77` 永不落地 → **从第一条开始** |
| `serve.py`（支持 Range） | `1(到 209.0)` | ✅ `ct=19.93` 继续推进，`idx=6` → 从第 7 条继续 |
| `file://` | `1(到 209.0)` | ✅ 正常 |

   实测：不带 Range → `200 + Accept-Ranges: bytes`；带 Range → **`206 bytes 0-99/1129580`（100 字节）**。

### 23.13 ✅ 架构改动：改为「一词一个 MP3」，彻底删除时间轴（2026-10-14）

**用户反馈**：暂停 → 按上一词/下一词 → 再播放，**会先读了上一个词的中文**，再读选定的词。

#### 定位过程（用内容判据，纠正了我一次错误的验证方法）

一开始我按 `build_vocab.py` 里的同一个下标公式去核对时间轴，得出"56/56 吻合"——
**这是循环论证，等于没验**。改用内容判据（词边界必须是**长**静音）后才暴露真相：

```
检测到静音 126 段（应为 113）→ 多出 13 段
静音#7  12.86→13.21 (0.351s)  = 词4.end & 词5.start    ← 词边界只有 0.35s
静音#17 27.96→29.09 (1.132s，奇数下标) = 词边界
静音#22 36.40→37.52 (1.118s，**偶数下标**) = 词边界   ← 奇偶性已翻转！
```

**根因**：`tracks_from_gaps()` 用 `inter = [(starts[i], ends[i]) for i in range(1, len(starts), 2)]`
取**奇数下标**当词边界 —— 这是在赌"检测到的静音严格交替"。而
`GAP_EC = GAP_WORD = 0.5`（**两种间隔等长、根本无法区分**），
片段内部停顿一旦被多检出一段，奇偶性就翻转，之后**所有**词边界都取到「英↔中」那一段 →
`start` 指向该词中文起点（也就是上一个词的中文）→ 播放即"先读上一次的中文"。

#### 并且发现这条路**修不干净**

试着改成"解析式时间轴"（按拼接顺序累加各段帧数）后，又暴露第二个问题：
`concat()` 用 `-c copy` 直拼时，**每段自带的 LAME gapless 元数据会让 junction 被裁掉一点**，
实测一页 57 词差 **3.27s** → "输入帧数之和 ≠ 输出帧数"，按帧累加也对不上；
改成重编码后反而差 **9.07s**。

> 结论：只要"从整页 MP3 里按时间轴 seek 到某词"这个设计成立，
> 时间轴就只能**推断**，而推断已经连续出错。**这不是调参能解决的，是设计问题。**

#### 改动：一词一个 MP3（`audio/pNNN_iii.mp3`）

| 层 | 变化 |
|----|------|
| 构建 | 每个词输出一个独立 MP3（`[en][间隔][cn]`，重编码成干净单文件）；整页 MP3 保留，**仅供「下载本页 MP3」**，用 `-c copy` 无损直拼 |
| 数据 | `tracks[k]` 从 `{start,end}` 改为 `{url}` —— **不再有任何时间轴** |
| 播放器 | 删掉整套 seek 机制（`applyPendingSeek` / `seekTo` / `trackAt` / `checkSeekable` / `pendingSeek` 及其状态量），改为换 `audio.src` |
| 进度条 | 从"整页进度"改为"**当前这一条**的进度" |
| 词间停顿 | 由播放器补 `WORD_PAUSE_MS = 650ms`（音频文件里不再含尾部静音） |

**一并消失的问题**（都不再需要处理）：
① 静音不可区分导致的词边界错位；
② `-c copy` 直拼的 gapless 逐段裁切；
③ **服务器不支持 HTTP Range 时整段音频不可 seek**（§23.12 那个大坑，现在 seek 只发生在单个几百 KB 的小文件内，且只在拖进度条时）；
④ iOS 在元数据就绪前丢弃 `currentTime` 赋值。

### 23.14 下载功能：保留整页 MP3 + 文件名可改（2026-10-14）

**用户拍板**：下载是最初指定的功能，**必须保留**（不采纳"去掉整页 MP3 省 1 MB"的方案）；
并且**文件名与保存位置都应由用户自由决定**。

#### 浏览器限制（决定了能做什么）

| 打开方式 | 能否自选保存文件夹 | 依据 |
|----------|-------------------|------|
| `file://`（双击 index.html） | ❌ **不能** | `file://` 是 opaque origin，`showSaveFilePicker()` 调用即抛 `SecurityError` |
| `http://localhost`（Edge/Chrome） | ✅ **能** | localhost 属安全上下文，弹出系统「另存为」，**文件夹与文件名都能选** |

#### 实现

| 项 | 做法 |
|----|------|
| 入口 | 顶栏 `↓ MP3` → 弹出下载对话框（不是直接静默下载） |
| 文件名 | 输入框，默认 `初中英语词汇表_第1页.mp3`（取包名，自动选中便于直接覆写） |
| 记住上次 | 用 `localStorage` 记住上次用的文件名，二次打开自动回填 |
| 保存位置 | 优先 `showSaveFilePicker()`；失败或不可用 → 降级 `<a download>`（存默认下载目录，**文件名仍生效**） |
| 如实告知 | 按协议给不同提示；保存完成后 toast 里明确写"存到了哪" |
| 关闭 | 取消按钮 / Escape / 点遮罩 |

#### ⚠️ 踩到的一个"看着能用其实不能用"的坑

**`typeof window.showSaveFilePicker === 'function'` 在 `file://` 下同样为 `true`** ——
能力检测通不过，它只在**调用时**才抛 `SecurityError`。
若照这个判据写提示文案，就会向用户**错误承诺"文件夹可以自己选"**。
所以：**文案按 `location.protocol` 判断，真正的分支在保存时用 `try/catch` 决定**（见 `openDl()` 注释）。

另修一处交互冲突：空格键原本是播放/暂停，对话框里输入文件名打空格会误触发 →
已加守卫（对话框打开、或焦点在 `input/textarea` 时不接管按键）。

#### 验证（CDP 真实浏览器，两种协议各跑一遍）

| 降级路径带**自定义文件名**触发 | ✅ `name=我的词汇 第1页.mp3` | ✅ |

静态探针 **16 PASS / 0 FAIL / 2 SKIP**；逐词播放与底部条场景全过。
