## 2. 计划书中「说得过头」的 6 条（必须修正措辞，否则会误导排期）

### 2.1 ❌「复用 make_audio.py，不改一行核心算法」（§0 / §3）

`extract_pairs()` 的抽取是完全**写死在这份 PDF 版式上**的：

```37:47:D:\WorkBuddy\2026-09-01-23-21-41\make_audio.py
def extract_pairs(idx):
    doc = pymupdf.open(PDF)
    page = doc[idx]
    words = page.get_text("words")  # x0,y0,x1,y1,word,block,line,wordno

    # 左列英文 (x < 250)，右列中文 (x > 380)，中间三列空白忽略
    left = [(w[0], w[1], norm(w[4])) for w in words if w[0] < 250]
    right = [(w[0], w[1], norm(w[4])) for w in words if w[0] > 380]
```

问题点：
- **绝对坐标硬编码**（`x<250` / `x>380`）→ 换一份页宽、页边距不同的词汇表 PDF，**直接全错**。
- `y_gap=24`（单位是 PDF point，不是计划书写的 px）、最近邻回退阈值 `<=30` 同样是拍出来的常数。
- `PDF` 是模块级常量（`make_audio.py:5`），路径写死到某台机器的微信文件缓存目录。
- 表头过滤只认 `{"英文","中文"}` 两个词。

**结论**：现有代码只能证明「**这一份** PDF 能抽对」。计划书目标是「上传**任意** PET/词汇表 PDF」，两者之间差的正是 M1 的主要工作量。**"不改一行"是错的，应改为「不改合成链路，但抽取层必须参数化 + 自适应」。**

**修法（强烈建议）**：
1. 首选 `pymupdf` 的 `page.find_tables()`（≥1.23）替代坐标硬编码，得到真正的表格单元格，天然抗版式变化；
2. 保留坐标法作为 fallback，但把 `left_x / right_x / y_gap` 改为**按页自适应**：对词条 x0 做一维聚类，自动找出两列主簇；
3. 抽取失败（配对数 0 或中英比例失衡）时**不要静默输出空表**，而是回报「本页无法识别，请手动校对」→ 交给 P1 编辑界面。

### 2.2 ❌「自动识别词汇表页 = 复用全本扫描逻辑」（§4 P0）

**这段逻辑根本不存在**（§1 已核验）。它是 P0 项，必须计入排期：判断规则（左列拉丁字符占比 + 右列 CJK 占比 + 词条数 ≥ 8）要新写，且要在同一份自适应抽取层上实现。
**工时估算**：0.5–1 天。

### 2.3 ❌「断点续跑（沿用已验证规则）」（§11）

现有脚本是**单页/单次**执行，没有断点续跑。已产出的 manifest.csv 只能说明有人跑过批处理，但该批处理脚本**不在库中**（无法复用）。
**修法**：不要写"续跑"，直接写**内容级缓存**，更简单也更有效：

```
cache_key = sha256(json(pairs_sorted) + voice_en + voice_cn + rates)
命中 → 直接 concat 复用；未命中 → TTS 并写缓存
```
这同时把 §4 的「P2 同一文件再次合成免重跑」抬到 **P0**（见 §4.3：它还是抗滥用的第一道防线）。

### 2.4 ❌「模块直接 import 到 FastAPI 即可」（§3 / §8）

`make_audio.py` 有**全局可变状态**：`tmp` 在 `main()` 里 `global tmp`（`make_audio.py:98, 101`），`fix_page039.py` 也是靠 `m.tmp = ...` 外部注入。
Web 服务是并发的 → 两个请求同时覆盖 `m.tmp` 会**互相删对方的临时目录 / 写错输出**。
**修法**：不改算法，但必须把 `tmp / OUT_DIR / PDF` 从全局改成**显式参数**（或包成 `class SynthJob`）。这是"不改一行"做不到的，计划书应明说。

### 2.5 ❌「全书合成 = 一个请求」隐含假设（§4 / §7 / §10）

实测量级（基于 manifest 与代码）：
- 全书 **110 页 × 约 19 词 ≈ 2,100 词条**
- 每词 2 次 TTS 调用 → **≈ 4,200 次 edge-tts 请求**
- 串行（现有代码就是串行 `await`）：每次约 1.5s → **≈ 2 小时**（还不含重试与 ffmpeg 进程开销）
- 即使 4 路并发，也要 **40–50 分钟**

**这不能是 HTTP 请求-响应**，必须是「提交任务 → 后台队列 → 进度查询/SSE 推送 → 轮询取结果」。
而且：**2 小时连续请求微软免费端点，几乎必然触发限流/封禁**（现有 tts 重试 4 次 + 40s 超时说明它已经不稳）。
**修法**：全书合成只在「有账号 + 后台队列 + 并发≤4 + 缓存」的前提下开放（见 §6.2）。

### 2.6 ⚠️「先 edge-tts 原型，后换 Azure 合规化」（§0 / §10 M4）——顺序建议倒过来

换算一下 Azure 成本（数量级，具体以官网为准）：

| 项 | 估算 |
|----|------|
| 全书字符数 | 2,100 词 × (英文约 10 + 中文约 4) ≈ **3 万字符** |
| Azure Neural TTS 标准版 | 约 $15 / 1M 字符 → **全书 ≈ $0.45（≈ ¥3）** |
| 每月免费额度 | 约 0.5M 字符 ≈ **免费跑 17 本全书** |
| 音色 | `en-GB-SoniaNeural` / `zh-CN-XiaoxiaoNeural` **同名存在**，切换是替换一行调用 + 指定输出 `audio-24khz-48kbitrate-mono-mp3` |

**结论**：留 edge-tts 的理由只剩"省去申请 Key"，**成本完全不构成理由**。而 edge-tts 的代价是：无 SLA、随时挂、公开使用有 ToS 风险、**且会把风险落到你自己的出口 IP 上**（见 §5.1）。
**建议**：把 M4 提到 M2 之前（或与 M2 并行），做成 `TTS_PROVIDER=edge|azure` 双实现 + 同参数回退。公开上线必须 Azure。

## 3. 会直接卡死 M1/M2 的 4 个设计缺口

### 3.1 🔴 最严重：没有「每条词条的时间轴」，「单条重听 / 单条循环」做不出来

§4 P1 要「点击某词条单独播放」，§6 状态机有 `mode === single` 循环播当前条。
**但现有产出只有一个拼接好的整页 MP3，没有任何每条的时间点信息。** 前端无法知道第 7 个词从第几秒开始。

**必须写进接口契约**（这是计划书最大的空白）：

```json
POST /synthesize → 200
{
  "job_id": "...",
  "pages": [{
    "page": 3,
    "mp3_url": "/audio/xxx/page003.mp3",
    "duration": 58.2,
    "tracks": [
      {"i":1,"en":"peaceful","cn":"宁静的","start":0.00,"end":2.35},
      {"i":2,"en":"...","cn":"...","start":2.85,"end":5.10}
    ]
  }]
}
```
`start/end` 由后端对每个 clip 跑一次 ffprobe 累加得到（**顺带把 0.5s 间隔也计入，前端不要自己猜**）。
前端 `单条重听 = audio.currentTime = track.start`；`单条循环 = 播完 track.end 再 seek 回 start`。

### 3.2 🔴 会退化成"重下整页"：`mode=single` 不要改 `audio.src`

切 `src` 会触发重新下载/解码 → 有明显的"重播空洞"。单条重听/单条循环**必须用 seek**（依赖 3.1 的时间轴），而不是换文件。

### 3.3 🔴 §6 的 `breakIt` 布尔量存在竞态缺陷，建议换成"代次计数器"

计划书自己说了这是"最易踩的坑"，但给的方案仍有 bug：如果用户点「停止」的瞬间音频正好自然播完，`onended` 先执行、`breakIt = true` 后落 → **这个 true 会残留**，导致下一次点播放时第一条"播一下就停"。

更稳的写法（推荐直接采纳）：

```js
let gen = 0;                       // 代次：任何 play/stop 都 +1
function play(i) {
  const my = ++gen;
  audio.currentTime = tracks[i].start;
  audio.play();
  audio.onended = () => {
    if (my !== gen) return;        // 已被更新的播放或停止取代 → 静默退出
    if (mode === 'single') play(i);
    else if (mode === 'loopPage') play((i + 1) % tracks.length);
    else if (mode === 'seqAll') nextOrStop(i + 1);
  };
}
function stop() { gen++; audio.pause(); }   // 无需手工清零任何标志
```
不再需要 `breakIt`，也就不存在"忘记清零"这一类 bug。

### 3.4 🔴 iOS Safari 会拦住循环（家长用 iPad 是主场景）

`onended` 里调用 `play()` **不在用户手势栈内**，iOS 可能拒绝自动播放，表现为"播完一条就静默停下"。
**必须做**：首次用户点击「开始」时，用同一个 `audio` 元素 `play()` 后再 `pause()`，完成解锁；并保证全程**只用一个 audio 元素**（多元素会被 iOS 逐个限制）。

### 3.5 🟡 `seqAll`（全书顺序）的数据来源未定义，且 110 页整包 ≈ 44MB 不可用

110 × 约 400KB ≈ **44MB 单个 MP3**，家长手机流量/等待都不可接受。
**修法**：`seqAll` 改成**按页懒加载**——播完当前页再取下一页（可预取下一 `src`），前端维护 `pageIndex`，跨页无缝续播。后端提供 `GET /audio/{job}/{page}.mp3`。
这与 3.1 的时间轴方案天然兼容（每页各自有 tracks）。

## 4. 其他值得补的修正

### 4.1 上传安全要再加三层
计划书 §11 只写了「类型白名单 + 大小上限 + 临时目录隔离 + 过期清理」，还要补：
- **不要在进程内直接 `pymupdf.open(用户文件)`**：解析在**子进程 + 硬超时（如 20s）+ 内存上限**中跑，防解析炸弹/死循环；
- **文件名绝不参与路径拼接**（路径穿越）：一律用 `uuid4()` 做文件名，原始名只存 DB 字段用于展示；
- **下载 URL 用 HMAC 签名 + 过期**，杜绝 `job_id` 可枚举（匿名模式下没有账号，IDOR 依旧存在）；
- 磁盘配额（临时目录总大小上限），满了直接拒绝新任务而不是写爆磁盘。

### 4.2 ffmpeg 拼接的隐性依赖
`concat demuxer + -c copy` 要求所有片段编码参数**逐字节兼容**。现在 edge-tts 输出（24kHz/48kbps mono mp3）与 `libmp3lame` 生成的静音（`make_silence`，默认码率）恰好能拼上，属于**侥幸可行**。切换 Azure 后必须显式指定同一输出格式（`audio-24khz-48kbitrate-mono-mp3`），否则拼接会出错或时长错乱。
更稳的做法：最终拼接改成 `-c:a libmp3lame -q:a 5` 重编码（慢一点，但参数无关）。**这一条要在换 TTS 时同步验证。**

### 4.3 缓存要抬到 P0（计划书放在 P2）
匿名公开场景下，缓存 = **抗滥用的第一道防线 + 降本 + 提速**三合一。词表类内容重复度极高（同一份 PET 表会被多人上传），命中率会很可观。

### 4.4 `pymupdf` 还能顺手解决「扫描件 PDF」
计划书 §13 讨论了 jpg 走 OCR，但漏了一条：**扫描版 PDF 现在会静默返回 0 词条**（没有文字层）。
其实 `page.get_pixmap()` 就能把任意 PDF 页渲染成图 → 走同一条 OCR → 坐标重建链路。**多写 5 行，就把「扫描件 PDF」和「JPG」合并成同一条支线**，值得顺手做。

### 4.5 §13 的评估整体认同
txt / docx 确实是"白送级"，jpg 风险判断也对，且「无结构文本整段朗读要另开模式，别混进配对解析器」这条建议很正确，建议**原样保留**。
JPG 补充一点：手机随手拍加 OCR 的错误会集中在**中文错字**上，P1 编辑界面确实是唯一可行的兜底，所以 **P1 编辑界面不是可选优化，而是 JPG 支线的准入前提**。

### 4.6 部署方案（§9）缺一个零成本选项，且 B 需要先验证
- **方案 B（workbuddy.link）**：必须先验证是否支持「常驻 Python 进程 + 执行外部 ffmpeg 二进制」。若它只是静态/CDN 托管，则**直接不可行**（本应用必须有后端常驻。"只支持静态"这一种可能判死一半）。**在写任何代码之前先花 10 分钟验证**。
- **方案 C 的更好形态**：`Cloudflare Tunnel`（或 Tailscale Funnel）——免费、自动 HTTPS、无需公网 IP，把本机服务安全地临时暴露给家长群，比内网穿透工具稳。计划书漏了这个选项，建议补为 **C+**。
- **方案 A** 成本其实不高：一台 1C2G 小 VPS（约 ¥30/月）+ Docker 镜像（内含 ffmpeg）+ 单进程 uvicorn。**只要上了 Azure TTS，方案 A 就完全可控。**

### 4.7 与「复用已有启动器」结合
`start_jev.bat` / `stop_jev.bat` 那套（端口文件、PID 文件、日志落盘、自动 kill 旧实例、自动开浏览器、失败转前台看错误）是**已经踩过坑的产物**（pythonw 无控制台、stdout 为 None 等都处理了）。方案 C 直接拷贝改造，能省掉一整轮调试。

## 5. 「匿名公开」与「账号隔离」的核心权衡

### 5.1 先看清匿名公开的真实风险：**IP 连坐**

edge-tts 走的是**你服务端的出口 IP**去请求微软免费端点。匿名公开意味着：
> 任何一个陌生人刷你的站 → **请求全都记在同一个 IP 头上** → 微软限流/封的是**你** → 全部用户同时不可用，且你自己本地开发也被封。

**这才是匿名公开的第一风险，不是"数据隔离"。**
另外还有两个：① 无上限的计算任务（2 小时/次）→ 单机被打死；② 磁盘/带宽被塞满。
**共同解法**：公开上线就上 **Azure（带 Key、带 SLA、按量计费）**——此时请求不再"蹭"共享端点，IP 连坐风险消失，成本仍只有约 ¥3/全书。

## 6. 两套方案建议

### 6.1 方案 A：匿名公开（无登录）

**适用**：链接丢进家长群/同事群，用完即走，不指望沉淀数据。

**设计原则：把公开面做成「只读为主 + 极窄写入」。**

| 项 | 建议 |
|----|------|
| 内容形态 | **预置词表库**（把已验证的 PET 110 页直接装进去）**公开只读**，含循环朗读 / 单条重听 / 下载 —— 覆盖绝大多数需求，**滥用面 ≈ 0** |
| 上传 | 保留，但**严格限流**：per-IP 令牌桶（如 5 页/小时、20 页/天）、单次 ≤ 3 页、PDF ≤ 20MB 且 ≤ 50 页 |
| 全书合成 | **匿名不开放**（资源黑洞）。只允许单页/少页 |
| 并发 | 全局 TTS 信号量 ≤ 4；任务队列上限（如排队 > 20 则直接返回"繁忙"） |
| 缓存 | **P0**，`sha256(pairs+voice)` 命中直接返回（抗滥用核心） |
| 存储 | **零持久化**：源 PDF TTL 30 分钟，成品 TTL 2 小时，定时清理；不引数据库 |
| 状态 | 内存字典即可（单 uvicorn 进程）；**千万别开多 worker**（内存态会分裂） |
| 下载 | HMAC 签名 URL + 短过期；文件名用 uuid4 |
| 防刷 | 一次性 Cookie 令牌 + 简单算术题/滑块即可拦住脚本（**不要用 reCAPTCHA，国内不可用**） |
| 免责 | 页脚注明"仅供个人学习使用"；若用 edge-tts，注明"非官方接口，可能随时不可用" |
| 止血 | 提供 `UPLOAD_ENABLED=false` 之类的**一键 kill switch**：被刷时立刻退化成"只读预置词库" |

**优点**：实现最快，无账号体系，隐私最好（不存任何东西）。
**代价**：用户无法保存修正过的词表/进度；一旦被刷，只能靠限流硬扛（所以 Azure 几乎是必需的）。

---

### 6.2 方案 B：账号隔离（登录 + 多用户）

**适用**：想让用户"回来看自己的词表/错词修正/进度"，或打算长期公开运营。

| 项 | 建议 |
|----|------|
| 鉴权选型 | **不要自建密码库**（要处理找回、撞库、加密）。家庭/班级场景用 **邀请码 + 设备令牌** 就够；再上一层用**邮箱/手机验证码**或**微信扫码** |
| 会话 | `HttpOnly + Secure + SameSite=Lax` Cookie；HTTPS 必须 |
| 隔离第 1 层（接口） | 每个请求先解析 `user_id`，**所有查询强制带 `user_id`**，禁止"按 job_id 直查" |
| 隔离第 2 层（存储） | `/data/users/{uid}/{job_id}/`，物理隔离（比单目录+前缀更好审计） |
| 隔离第 3 层（授权） | `GET /download/{job_id}` **必须校验归属**：`job.user_id == current_user.id`。**这是最容易漏的高危点（IDOR）** |
| 任务模型 | 必须**队列化**：`jobs(id, user_id, status, progress, created_at, expires_at)`，前端轮询或 SSE 看进度 |
| 配额 | **账号 + IP 双轨**（防小号刷）；账号可给更高额度；全书合成只对账号开放 |
| 数据生命周期 | 源文件 **24h 自动删**（默认不留原文）；成品 7 天；提供「删除我的数据 / 导出」 |
| 隐私 | 素材多为未成年人学习材料 → **最小化收集**（不要手机号就别要），隐私说明一页纸 |
| DB | **SQLite 足够**（单机低并发），别一上来上 Postgres |
| 分享（账号版真正优于匿名的点） | 做**只读分享链接**（可选密码 / 有效期 / 可撤销），发给别人用 —— 既满足"发给别人用"，又能随时断流。**这比全站开放匿名可控得多** |
| 合规 | 公开运营 = 向公众提供服务 → edge-tts 的灰色使用不再可辩护 → **Azure 从第一天就上** |
| 管理面 | 极简 admin：看任务量、封 IP/封号、清缓存 |

**优点**：可沉淀数据、可分享、可限额、可止血、责任清晰。
**代价**：开发量约 +2–3 天；多一套隐私义务。

---

### 6.3 📌 推荐：第三条路（组合拳，解耦两个诉求）

> 把「发给别人用」和「保存自己的东西」这两个诉求**解耦**，各自用最轻的方案满足。

```
① 匿名只读：预置 PET 词库（110 页）公开可用   ← 覆盖 90% 家长需求，滥用面≈0
② 匿名受限上传：严格限流、单页/少页、不存盘   ← 满足"我也有个表"
③ 可选轻账号：想存修正词表/进度时才引导登录   ← 渐进式，不做登录墙
④ 全书合成：仅登录 + 后台队列 + 缓存          ← 资源黑洞只对账号开放
⑤ 分享：账号版生成可撤销只读链接              ← "发给别人用"的正解
```

**为什么推荐**：
- 不动不动就上登录墙，会让"发个链接给家长群"这个**核心诉求**直接失败（对方要注册，转化率极低）；
- 但也不该把 2 小时/次的全书合成暴露给匿名流量；
- 把最重的操作（全书/上传）挂在账号上、最轻的操作（听预置词库）免费公开，**风险与价值正好对齐**。

### 6.4 决策表

| 你的真实意图 | 选 |
|--------------|-----|
| 就发给几个朋友/家长群，能用就行，不折腾 | **方案 A（匿名）** + 预置词库为主，**关掉匿名上传** |
| 想长期公开运营、有人会反复用 | **方案 B（账号）** + Azure |
| 想"发链接给家长"**同时**想"自己保存修正结果" | **§6.3 组合拳（推荐）** |

## 9. 总体评价

计划书**技术判断几乎全对**（CORS 必须后端、音色不能退回 SAPI、统一解析层、OCR 复用坐标重建、无结构文本另开模式）——这些都是有实战经验的判断，不是拍脑袋。
主要问题集中在**三处乐观**：
1. **对"复用"的乐观**：把"这一份 PDF 的解法"当成"任意 PDF 的解法"（§2.1 / §2.2 / §2.3）；
2. **对"规模"的乐观**：全书 ≈ 4,200 次 TTS ≈ 2 小时，被当成一个接口调用（§2.5）；
3. **对"合规"的乐观**：把 Azure 当成"M4 有空再做"，但成本只有约 ¥3/本，且它是**匿名公开能否成立的前提**（§2.6 / §5.1）。

另外最大的一处**设计空白**是 **tracks 时间轴**——P0/P1 的大量交互（单条重听、单条循环、seqAll 续播）都依赖它，计划书通篇没提。

修掉 §2 的 6 条 + §3 的 4 个缺口，这份计划就是一份**可以直接开工**的计划。
