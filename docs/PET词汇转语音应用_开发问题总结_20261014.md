# PET 词汇转语音应用 · 开发问题总结

**日期**：2026-10-14
**范围**：形态 ③（纯 HTML 播放器）从草稿到可交付
**一句话**：今天修掉 **5 个功能缺陷 + 1 次架构改动**；其中 **4 个缺陷源于同一个未被识别的假设** ——
"可以从整页 MP3 里按时间轴精确 seek 到某个词"。而支撑它的时间轴只能靠**推断**
（数静音 / 数帧），今天连续三次都推断错了。最终把设计改成「**一词一个 MP3**」，这一类问题整体消失。

---

## 一、功能缺陷（按发现顺序）

| # | 现象 | 根因 | 修复 |
|---|------|------|------|
| 1 | 「第 1 页是 57 词，网页只有 40 词」 | 我把 `--max-words 40` 这个**估算值**当成了真实分页，且没去核实。docx 的 XML 里确实没有分页信息（`lastRenderedPageBreak` 0 处、显式分页符 0 处） | 用 **Word COM** 逐段读 `wdActiveEndPageNumber` 拿到真实页码：**总 39 页，第 1 页 = 57 词**（与用户所说一致），导出 `word_pages.json` 供复用；解析器新增 `--word-pages` / `--page N` |
| 2 | 「第一次点开始没反应，得先点暂停、再点开始才播」 | `playFrom()` 里那个所谓「iOS 音频解锁」块：`audio.play().then(() => audio.pause())` —— **pause 是异步（微任务）执行的**，把紧接着发出的真实 `play()` 一起掐掉 | **整块删除**。真实 `play()` 本就在点击回调的同步调用栈里，自己就完成解锁；那个额外的 play/pause 只是制造竞态 |
| 3 | 「点任意一条重听，结果从第一条开始」 | `applyPendingSeek()` 用 `audio.seeking === true` **提前**清掉 `pendingSeek`。而 seek 期间 **Chrome 立刻返回新值、Safari 等返回旧值** → 于是拿旧位置算 `trackAt()`，把高亮连同 `idx` 一起拽回去（旧位置≈0 时正好是第 1 条） | 改为**只有读回来的位置确实等于目标（±0.35s）才算落地**；`trackAt(!isFinite)` 保持当前条不动 |
| 4 | 通过 HTTP 预览时所有 seek 失效（而双击 `index.html` 正常） | Python 自带 `http.server` **不支持 HTTP Range、也不发 `Accept-Ranges`** → Chromium 判定整个音频不可 seek：`audio.seekable.length=1` 但 `end(0)=0` | 新增 `serve.py`（支持 Range 的静态服务器，实测 Range 请求返回 **206 + Content-Range**）；播放器增加「环境不可 seek」的**显式提示**，不再默默出错 |
| 5 | 「暂停 → 上一词/下一词 → 播放，会先读上一个词的中文」 | `tracks_from_gaps()` 取**奇数下标**静音当词边界 —— 在赌"检测到的静音严格交替"。而 `GAP_EC == GAP_WORD == 0.5`（**两种间隔等长、根本无法区分**），片段内部停顿一旦多检出一段，奇偶性就翻转 → 之后**所有**词边界都取到「英↔中」那一段 → `start` 指向该词中文起点（即上一个词的中文） | 见 #6（改为不再需要时间轴） |
| 6 | **架构改动** | 试着改成"按拼接顺序累加各段帧数"也不行：`-c copy` 直拼时每段自带的 gapless 元数据会让 junction 被裁掉一点，**一页 57 词差 3.27s**；改成重编码反而差 **9.07s** → "输入帧数之和 ≠ 输出帧数" | **一词一个 MP3**：`tracks[k]` 从 `{start,end}` 改为 `{url}`，播放器**删掉整套 seek 机制**（`applyPendingSeek`/`seekTo`/`trackAt`/`checkSeekable`/`pendingSeek`） |

### 架构改动后一并消失的问题

① 静音不可区分导致的词边界错位；② `-c copy` 直拼的 gapless 逐段裁切；
③ **服务器不支持 HTTP Range 时音频不可 seek**（#4 那个大坑）；④ iOS 在元数据就绪前丢弃 `currentTime` 赋值。

### 实测复现与验证

用户质疑的确切场景（CDP 驱动真实浏览器）：

```
C  暂停      高亮=2  文件=p001_003.mp3   ct=1.28
C2 下一词    高亮=3  文件=p001_004.mp3   ct=0.00
C3 再下一词  高亮=4  文件=p001_005.mp3   ct=0.00
D  播放      ct 从 0 推进，高亮始终=4        ← 不可能串到上一个词
E  点第30行  高亮=29 文件=p001_030.mp3  稳定
```

## 三、三条真正可复用的规则

1. **验证必须独立于实现。** 用同一套公式、同一个函数去核对它自己，结果永远是绿的 —— 那种"通过"没有任何信息量。
2. **凡是"推断出来的坐标/时间轴"，都要有独立真值来源。** 数静音、数帧都是推断；只要推断参与定位，就一定会错。
   更好的策略是**让结构本身不含歧义**（一词一个文件），而不是靠算法去恢复歧义。
3. **"能跑" ≠ "对齐"。** 从"没声音"到"有声音"是能跑；从"有声音"到"读的是对的那个词"才是对齐。两者必须用**不同的断言**覆盖 —— 今天正是"按钮显示暂停但实际静音"骗过了旧探针。

## 四、已沉淀为门禁/工具的东西

| 工具 | 作用 |

| `_probe_pack.py` | 包运行时结构断言；**挂钩 `HTMLMediaElement.prototype.play/pause`**，断言首次点击只能调一次 `play`（旧版只断言按钮文字，被"假暂停"骗过） |
