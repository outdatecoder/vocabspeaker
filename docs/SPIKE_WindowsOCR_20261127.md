# SPIKE 报告 · Windows 内置 OCR 能不能用（2026-11-27）

> 目的：回答一个 go/no-go 问题 —— **Windows 自带的 OCR 能否把词汇表页面识别成可用的「英文 + 中文」词条？**
> 结论先说：**本机不达标，且这条路线不能随便携包交付。** 但归因不是"Windows OCR 差"，而是本机**没有英文 OCR 语言数据**。

---

## 1. 方法（为什么这个结论不是"看着像不行"）

| 项 | 做法 |
|---|---|
| 引擎 | `Windows.Media.Ocr`（WinPS 5.1 + WinRT，`OcrEngine.TryCreateFromLanguage`） |
| 样本 | 合成页：22 条 PET 词汇，5 列（`#` / Word / Phonetic / POS / 中文），用 Edge headless 渲染成 1654×1400 PNG |
| 标准答案 | 与生成图片同源的 `gt.tsv`（22 条真值），**不是** OCR 自己的输出 —— 满足 AGENTS R1「验证必须独立于实现」 |
| 判据 | ① 英文召回 ② 中文召回 ③ y 轴配对准确率 ④ 列的 x 坐标是否可分 |
| 及格线（事先写死） | 英文召回 ≥90% 且 配对 ≥90% |

**样本是"渲染得极干净的合成页"，比手机照片简单得多**，所以下面的数字是**上限**，不是期望值。
## 2. 结果

| 指标 | 数值 | 及格线 |
|---|---|---|
| 可用的识别语言 | `es-ES` / `ja` / **`zh-Hans-CN`**；**`en-US`、`en-GB` 均 `NOSUPPORT`** | — |
| 实际使用引擎 | `zh-Hans-CN`（中文模型认英文） | — |
| 耗时 | **341 ms**（单页） | — |
| OCR 行数 | 83（每格一行） | — |
| 英文召回（精确） | **11 / 22 = 50%** | ≥90% ❌ |
| 英文召回（模糊 ≥0.8） | 16 / 22 = 73% | ≥90% ❌ |
| 中文召回 | 20 / 22 = 91% | — |
| 同一行内 en+cn 共现 | **0 / 22 = 0%**（引擎按单元格切行） | — |

| 列可分性（左边界 x） | **可分**：序号≈90 / Word≈152 / 音标≈435 / POS≈731 / 中文≈816 | ✅ |

## 4. 归因

1. **不是引擎的普适结论**：本机 `AvailableRecognizerLanguages` 只有 `es-ES / ja / zh-Hans-CN`，`C:\Windows\OCR\` 里也没有 `en-us`。用**中文模型**认英文单词，出现 `ar→m`、`i→l` 这类系统性错误是必然的。
2. **结构性噪声其实可解**：x 坐标非常稳定（Word 152 / 音标 435 / 中文 816），说明"按 bbox 归列"完全可行 —— 问题只在**字符识别精度**，不在版式理解。
3. **更硬的约束在交付形态**：Windows OCR 依赖**目标机器**的系统语言包。本项目交付的是"拷给别人双击就用"的便携文件夹，对方机器没有 OCR 语言组件时功能直接不存在，且无法随包携带。

> 即使装上 en-US 语言包把英文召回拉到 90%，也**只解决"你本机能用"**，解决不了"交付给别人能用"。

## 5. 结论与下一步

| 判断 | 结论 |
|---|---|
| 作为**可交付**功能 | ❌ 否决（依赖目标机语言包） |
| 作为**本机自用** | ⚠️ 当前不达标（英文 50%）；装 en-US 语言包后可复测，但需管理员权限、仍是系统级改动 |
| 下一步 A | 必须交付 → 只剩自包含引擎（RapidOCR，+150~200 MB），先确认体积预算 |
| 下一步 B | 可接受"仅本机" → 装 en-US 语言包后复跑本 spike（样本与脚本已留，10 分钟出结果） |
| 兜底 | 砍掉 OCR，上传卡给实话术：「扫描件/照片请先用手机扫描 App 或 Word 转成 docx/pdf」 |
