# PET 词汇转语音应用 · 形态选型对比：Web 应用 vs EXE

> 日期：2026-10-12
> 前置决策：**不做公开上线**（本轮已拍板）→ 风险面只到"自己 + 少量分享"，Azure 降为可选
> 数据口径：**「实测」= 本机实际测量**；「估算」= 基于实测组件体积推算，会标注

---

## 0. 先给结论

| 关注点 | 赢家 | 一句话 |
|--------|------|--------|
| **开发难易** | **Web 完胜** | 已有可运行母版（`jev_stock_app.py` 纯标准库 + `start_jev.bat`）；EXE 额外 2–4 天，且调试体验退化 |
| **占用空间** | **纯 HTML 播放器完胜** | 20–40 KB vs EXE **约 90–110 MB** vs 本地 Web（含 Python 环境）**约 200 MB** |
| **用户易用性** | **看设备，结论分叉** | Windows 家长：EXE 最好；**iPad/手机家长：EXE 直接出局，只有「预生成 MP3 + 单文件 HTML」这条路通** |

**推荐：同源双形态（甚至三形态）**，不是二选一 —— 见 §5。核心洞察是：
> **「抽取/合成」和「循环播放」是两个可以拆开的关注点。**
> 家长真正要的只是"循环听写"，而 MP3 你已经有了（110 页 / 41.8 MB）。所以给家长的那一份，**可以完全不需要 Python、pymupdf、ffmpeg，甚至不需要联网**。

## 1. 先厘清：其实不是两个形态，是四个

「Web 应用」这个词把差别很大的东西混在一起了，对你这个场景必须拆开：

| # | 形态 | 是什么 | 谁用 | 需要装什么 |
|---|------|--------|------|-----------|
| ① | **本地 Web 服务** | 双击 bat → 自动起 `127.0.0.1:8765` → 自动开浏览器 | **你自己**（开发+使用） | 你的机器上有 Python |
| ② | **EXE 桌面应用** | 双击图标即用；内部**仍然可以**是个本地 Web 服务（只把 bat 的活搬进 exe） | 发给 Windows 家长 | 无 |
| ③ | **纯 HTML 播放器** | 一个 `.html` + 一堆 MP3，双击打开 | 家长/学生（最终消费者） | 无（零依赖） |
| ④ | **局域网 Web** | 本机开 `0.0.0.0` + 防火墙放行 → 手机/iPad 输 IP 访问 | iPad 场景 | 无，但要会输 IP |

> ①③④ 的「占用空间」和「易用性」差异极大，混在一起讨论会得出错误结论。

## 2. 维度一：开发难易

### 2.1 工作量对比

| 形态 | 相对本地 Web 的额外工作量 | 主要难点 |
|------|--------------------------|----------|
| ① 本地 Web（零依赖 `http.server`） | **基准 0** | 无。母版可直接改造 |
| ①' 本地 Web（FastAPI） | +0.5 天 | pip 依赖链、启动脚本 |
| ② EXE（PyInstaller） | **+2~4 天** | 见 §2.2 六个坑 |
| ③ 纯 HTML 播放器 | **+0.5 天** | 前提是后端已产出 tracks 时间轴 |

**① 的基准较低，但要分清「哪部分真能复用什么」**（⬅️ 本节已按核实结论修正，勿再说"整套复用"）：

| jev 项目的组成 | 规模（实测） | 本项目能否复用 |
|----------------|--------------|----------------|
| `start_jev.bat` / `stop_jev.bat` | 各约 150 行 | ✅ **几乎全可复用**，只改 3 个常量（脚本名 / 起始端口 / 窗口标题）。与业务模型无关 |
| `_log` / `_out` / `_is_tty` | 约 70 行 | ✅ 直接可用（`pythonw` 无控制台时 `sys.stdout is None` 的处理已踩过） |
| `Handler.log_message` 覆写 | 5 行 | ✅ 直接可用（默认写 `sys.stderr`，无控制台会抛 `AttributeError` 导致每个请求崩） |
| `_port_available()` + `bind_server()` | 约 30 行 | ✅ **尤其值钱**：Windows 上 `SO_REUSEADDR` 会让"已被占用的端口"也 bind 成功 → 旧实例抢答请求（表现为"改了代码却不生效"）。这个坑它是用"独占探测"绕过的 |
| `main()` 的 `app.port` / `app.pid` / 自动开浏览器骨架 | 约 35 行 | ✅ 可用 |
| 「单文件 Python + 顶部内嵌 HTML 字符串」的组织模式 | — | ✅ 模式可用 |
| **`Handler` 的请求层**（路由 + `_send` + `do_GET`/`do_POST`） | 约 60 行 | ❌ **要重写**。见下方"模型不同"说明 |
| 股票业务逻辑（决策/回测/纸盘） | **约 1,100 行（占该文件 80%）** | ❌ 与本项目无关 |

**「模型不一样」是真的，而且是根本性的**：

| | jev 项目 | 本项目（PET） |
|---|----------|---------------|
| 请求模型 | 无状态 / 同步 / 纯 JSON 短请求 | 文件上传 + **小时级后台任务** + 流式进度 |
| 传输 | JSON 进出 | **multipart 或原始字节进**、二进制 MP3 出 |
| 并发 | `ThreadingHTTPServer` 一线程一请求（唯一线程只用来开浏览器） | 需要任务队列 + 并发信号量（后台跑 TTS） |
| 响应 | `_send()` 固定带 `Content-Length`（**与 SSE 天然不兼容**） | 需要 `text/event-stream` 流式写 + `flush` |
| 静态文件 | ❌ 没有（`do_GET` 只服务 "/" 一个内嵌 HTML，其余 404） | 需要音频静态服务（可选 `Range`） |

结论：**jev 可供复用的是「连接层与启动器」（约 230 行），不是「请求层」。** 即便如此仍然划算——`_port_available` 和 bat 那套是纯赚的；但要按"重写 Handler（约 200–300 行）"来估工时。

> ⚠️ 另有一项**实测发现的坑**（见实施计划 §9.1）：pet 环境是 **Python 3.13.14**，而 **`cgi` 模块已在 3.13 被移除**（PEP 594），`python-multipart` 也未安装 → 标准库**不再自带 multipart 解析**。纯零依赖方案需改用"原始字节当请求体"上传（可行，因为客户端是我们自己写的）。

- 前端是 HTML/JS → **浏览器 DevTools 是最好用的调试器**（看时间轴、看 seek、看状态机，秒级迭代）。

### 2.2 打包 EXE 的六个坑（这才是"开发难"的真实成本）

1. **PyInstaller 未安装**，且 onefile 模式**每次启动要把约 150 MB 解压到临时目录** → 首启 **3–10 秒**白屏，家长会以为坏了。→ 建议用 `--onedir`，别用 onefile。
2. **资源路径变了**：`imageio_ffmpeg.get_ffmpeg_exe()` 在打包后路径失效，必须走 `sys._MEIPASS`，或干脆**把 ffmpeg 放在 exe 外面**（推荐，见 §3.2）。
3. **pymupdf 的 native DLL** 需要 `hidden-import` / `collect-dynamic-libs`，漏了就是运行时崩。
4. **没有控制台 → 错误不可见**。你现在没有 `app.log` 那套，会陷入"家长说打不开、你什么都看不到"。→ 直接把 jev 的日志机制抄过来。
5. **端口与浏览器**：EXE 里要自己挑空闲端口 + 自动拉起浏览器（bat 已经做过，逻辑搬进 Python 即可）。
6. **杀软误报 + SmartScreen**：PyInstaller 产物是误报重灾区；未签名的 exe 首次运行会弹「Windows 已保护你的电脑」，要点「更多信息 → 仍要运行」。**根治需要买代码签名证书（约 ¥1–2k/年），否则只能写使用说明告知用户点一下。**

### 2.3 一个关键取舍：EXE 用什么做 UI

| 方案 | 说明 | 代价 |
|------|------|------|
| EXE = 内嵌本地 Web（自动开系统浏览器） | **复用现有 HTML，几乎零额外前端工作** | 会跳出浏览器窗口，体验像"网页" |
| EXE = 内嵌 WebView（`pywebview`/WebView2） | 看起来像原生应用，像样的桌面体验 | +0.5~1 天 + 引入 WebView 依赖 |
| EXE = 纯原生 GUI（Tkinter/PyQt） | 最"像软件" | **前端要全部重写**，且 MP3 循环播放要实现 `playsound`/`pygame` 手动管理 → **最贵，不建议** |

> 结论：**如果你已经打算做 Web，那 EXE 的最优解是「把 Web 包进 EXE」**，而不是另写一套 GUI。这样"开发难易"的差距就只剩打包那 2–4 天。

## 3. 维度二：占用空间（实测 + 估算）

### 3.1 实测：你的依赖到底有多大

| 组件 | 实测体积 | 说明 |
|------|----------|------|
| Python 3.13.12 基础环境 | **48 MB** | `D:\WorkBuddy\.workbuddy\binaries\python\versions\3.13.12` |
| `pymupdf` | **52.9 MB** | PDF 抽取（native DLL 为主） |
| `imageio_ffmpeg`（含 ffmpeg 二进制） | **83.7 MB** | 其中 `ffmpeg-win-x86_64-v7.1.exe` 单个就 **83.6 MB** |
| `edge-tts` + `aiohttp` + `certifi` + `tabulate` | **约 3 MB** | 意外地小 |
| **`pet` 环境合计** | **153 MB** | 实测 `envs\pet` |
| 成品音频（110 页 MP3） | **41.8 MB** | 平均 **389 KB/页** |

### 3.2 各形态最终分发体积

| 形态 | 分发体积 | 口径 |
|------|----------|------|
| ① 本地 Web（**源码分发**） | 源码约 50 KB，**但要求用户自装 Python + 153 MB 依赖** | 实测依赖，实际约 200 MB **且要动手装** → 对非开发者不可行 |
| ② EXE `--onedir`（含 ffmpeg） | **约 150–180 MB** | 估算：stdlib 子集 20 + pymupdf 53 + ffmpeg 84 + 其他 5 |
| ② EXE `--onefile`（含 ffmpeg） | **约 90–110 MB** | 估算：压缩后；但**每次启动解压 150 MB → 慢 3–10s** |
| ②' EXE（**去掉 ffmpeg**） | **约 70–90 MB**（onedir） | 估算，见下方 💡 |
| ③ 纯 HTML 播放器 | **20–40 KB** | 只要一个 html |
| ③' 播放器 + MP3 数据 | +41.8 MB（可按页下发，甚至只给当前页 389 KB） | 实测 |
| ④ 局域网 Web | 同 ①（宿主机器承担） | — |

### 3.3 💡 机会一：直接删掉 ffmpeg，省 84 MB（>50%）

现在 ffmpeg 只干两件事：

1. **生成 0.5 s 静音片段**（`make_silence`）→ 其实**只需预先做好一个约 5 KB 的静音 MP3**，随包附带或 base64 内嵌，**完全不需要 ffmpeg**。
2. **拼接**（`concat_files`，`-f concat -c copy`）→ 关键在于：**所有片段都是同一编码参数的 MP3**（edge-tts 输出恒定 24 kHz/48 kbps mono），而 **MP3 本身就是帧结构，纯 Python 逐帧字节拼接即可**。所谓 `-c copy` 本质也是字节拼接。做法：剥掉每段开头的 ID3v2 标签与本段首帧的 Xing/Info 头，然后顺序拼接字节。

| 项 | 内容 |
|----|------|
| 代价 | 约 30 行需要小心写的代码（去 ID3/去 Xing/拼接）+ 一组对比测试（与 ffmpeg 版比时长与听感） |
| 收益 | **分发体积砍掉 84 MB**；少一个外部进程依赖（对杀软、沙箱、Docker 更友好）；合成更快（少 2,100 次进程 spawn） |
| ⚠️ 前提 | 必须锁定**单一输出编码**。edge-tts 天然满足；**若将来换 Azure，必须显式指定 `Audio24Khz48KBitRateMonoMp3`**，否则帧参数不一致就不能纯拼接（这也是上一版计划里那条"输出格式对齐"的意义） |

> 顺带：`mutagen` 也是纯 Python（约 200 KB），用来读每条时长，可替掉 2,100 次 `ffprobe` 子进程。

### 3.4 💡 机会二（更大）：把"抽取"留在你这边

`pymupdf` 那 52.9 MB **只在"用户自己上传 PDF"时才需要**。

- 如果家长**不需要自己传 PDF**，由你（或他们发给你）跑一次抽取 → **发给家长的包里既不需要 pymupdf、也不需要 ffmpeg、甚至不需要 Python**，只剩「30 KB 的 HTML + MP3」。
- 这直接命中你的实际场景：家长要的是**循环听写**，不是"自己处理 PDF"。

**这一条决定了最终答案：给家长的形态不该是 EXE，而该是"播放器 + 音频"。**

## 4. 维度三：用户易用性（这才是决定性的）

### 4.1 按人看

| 使用者 | ① 本地 Web | ② EXE | ③ 纯 HTML | ④ 局域网 Web |
|--------|-----------|-------|-----------|--------------|
| 你自己 | ★★★★★ 最好调试 | ★★ | ★★★ | ★★★ |
| Windows 电脑家长 | ★★★（双击 bat，有黑窗口，杀软可能弹） | ★★★★★（双击图标） | ★★★★（双击 html） | ★★ |
| **iPad / iPhone 家长** | ❌ **不可用** | ❌ **不可用**（仅 Windows） | ✅ 可用（有前提，需实测） | ✅ 可用（要会输 IP） |
| 完全不懂电脑的老师 | ★★ | ★★★★★ | ★★★★ | ★ |

### 4.2 关键分水岭：iPad / 手机

- **本地 Web 在手机上天然不可用**：`127.0.0.1` 只指手机自己。要能用必须：改成监听 `0.0.0.0` → **会弹出 Windows 防火墙授权框** → 还得让家长查本机内网 IP（`192.168.x.x`）→ 还得确保手机和电脑在同一 WiFi。**对非开发者基本等于劝退。**
- **EXE 只 Windows**，iOS/Android 完全出局。
- **纯 HTML + MP3** 是唯一可行的路：把文件夹拷进手机/网盘，用浏览器打开 `index.html`。

### 4.3 其他易用性细节

| 维度 | ① 本地 Web | ② EXE | ③ 纯 HTML |
|------|-----------|-------|-----------|
| 安装 | 解压 + 双击 bat | 双击 exe（含一次 SmartScreen 确认） | 双击 html |
| 防火墙 | 绑 `127.0.0.1` **不弹**（`jev` 就是这么做的）；绑 `0.0.0.0` 会弹 | 同左（内部仍是本地服务） | **完全不涉及** |
| 杀软 | 低风险 | **误报重灾区** | 无 |
| 启动速度 | 1–3 秒 | onedir 2–5 秒 / onefile **3–10 秒** | 即时 |
| 更新 | 改一行代码即可（自己用） | 要重打包重发 | 换一个 html 文件 |
| **无网络时能否用** | ❌ 不能（edge-tts 必须联网） | ❌ 不能（**EXE ≠ 离线**！TTS 仍走网络） | ✅ **能**（MP3 已生成，纯离线） |
| 分享给别人 | 要对方也装环境 | 发个 exe | 发个文件夹/网盘链接 |

> **「EXE ≠ 离线」这点很重要**：很多人以为打包成 EXE 就独立了，但 edge-tts 是**在线服务**，断网一样用不了。而**预生成的 MP3 + 播放器是完全离线的**——孩子在车上、飞机上、没 WiFi 的房间都能听写。这对"反复听写"这个核心场景是实打实的优势。

### 4.4 ⚠️ 需要实测的不确定项（别跳过）

纯 HTML 方案在 **iOS 上关于 `file://` 加载同目录 MP3 + 自动连播** 的行为比较特殊（历史上 iOS Safari 对本地文件的媒体加载与 autoplay 限制较严）。**这一条我不能凭记忆下结论，必须真机实测**：
- 测试：把 1 个 html + 3 个 MP3 拷进 iPad「文件」App，用 Safari 打开，试 ① 能否出声 ② 能否自动连播下一条。
- **若不行的退路**：把 MP3 + html 放网盘/对象存储用 `https://` 打开；或用 ④ 局域网 Web；或封装成一个"手机端小程序/H5 页面"（但这就又回到需要联网/服务端了）。

**建议：把这条实测放进"开跑前的门禁"（半天），它决定给家长发什么。**

## 5. 推荐：同源多形态（不是二选一）

```
一次开发，三处分发 —— 后端逻辑与前端播放器代码全部共享：

① 你自己用 ─── 本地 Web（零依赖 http.server，母版 jev_stock_app.py + start_jev.bat）
                ↳ 完整体验：上传 PDF → 抽取 → 合成 → 试听 → 导出
② 电脑端家长 ─ EXE（同一份代码用 pyinstaller --onedir 打包，内嵌本地 Web + 自动开浏览器）
                ↳ 体积优化：优先做 §3.3 的"去掉 ffmpeg"
③ iPad/手机家长 ─ 预生成 MP3 + 单文件 HTML 播放器（20–40 KB）
                ↳ 完全离线可用；这是"循环听写"场景的最优解
```

**为什么这么分**：
- 你自己要的**全部能力**（上传/抽取/编辑/合成），只有 ① 需要——它最贵，但只有你一个人用，打包不划算。
- 家长要的**只有循环听写**，②③ 都不需要 pymupdf，③ 连 ffmpeg/Python 都不要。
- 「循环朗读状态机」那套 JS（代次计数器 / iOS 解锁 / 懒加载）在 ② 和 ③ 里**是同一份代码**，写一次即可。

**顺序建议**：先 ①（跑通全链路）→ 再 ③（成本最低、覆盖 iPad、立刻能发给家长）→ 最后 ②（如果需要 Windows 桌面感）。

## 6. 决策速查表

| 如果你的首要目标是… | 选 |
|---------------------|-----|
| 自己先把功能跑通、改起来快 | **① 本地 Web** |
| 让家长"双击就能用"、有桌面应用感 | **② EXE（--onedir + 内嵌浏览器）** |
| 让家长在 iPad 上听写 | **③ 纯 HTML 播放器**（+ 实测 §4.4） |
| 体积越小越好 | **③**（20–40 KB）>> ②' 去 ffmpeg（70–90 MB）> ②（90–110 MB） |
| 离线可用 | **③**（① ② 都必须联网） |
| 开发最省事 | **①**，② 只比它多打包成本 |
